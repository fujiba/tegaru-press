# Tegaru Press

**Googleドキュメントで書いた記事を、画像ごと手軽に静的サイトへ。**

Tegaru Pressは、Googleドキュメントを使い慣れたライターや編集者が、技術的な知識なしにWebサイトのコンテンツを更新できるようにするためのGoogle Apps Script製ツールです。

## 主な特徴

- **いつものエディタで執筆**: Googleドキュメントの使いやすいインターフェースで記事を作成できます。
- **画像も自動処理**: ドキュメントに貼り付けた画像は自動で抽出され、記事と一緒にリポジトリへアップロードされます。
- **簡単なメタデータ管理**: 記事のタイトルや公開日などのフロントマターは、ドキュメント先頭のテーブルで直感的に管理できます。
- **ワンクリック公開**: Googleドキュメントのメニューから「GitHubへPush」を選ぶだけで、記事と画像がサイトに反映されます。

## 使い方

このツールは、サイトを管理する「開発者」と、記事を執筆する「ライター」の2つの役割を想定しています。

### 開発者向け：セットアップ

このリポジトリには2つのGASプロジェクトが含まれます。それぞれを別のGASプロジェクトとしてデプロイします。

- `library/` — 変換・Push処理の本体（スタンドアロンのGASプロジェクト）
- `caller/` — テンプレートドキュメントに紐付けるスクリプト（コンテナバインド）。ライブラリを呼び出す薄いラッパーです

#### 前提条件

- Node.js（`clasp` は `npm install` でローカルにインストールされます）
- Googleアカウントで [Apps Script API を有効化](https://script.google.com/home/usersettings)しておくこと（claspが動く条件です）

#### 1. クローンとclaspのログイン

```bash
git clone <このリポジトリ>
cd tegaru-press
npm install
npx clasp login   # ブラウザが開くのでGoogleアカウントで承認
```

#### 2. ライブラリのデプロイ

`library/.clasp.json` はGitに含まれていない（ローカル環境ごとに異なる）ため、自分で用意します。

**新規にGASプロジェクトを作る場合**（`.clasp.json` は自動生成されます）:

```bash
cd library
npx clasp create --type standalone --title "Tegaru Press Library" --rootDir src
```

**既存のGASプロジェクトに紐付ける場合**は、サンプルをコピーしてスクリプトIDを書き換えます:

```bash
cd library
cp clasp.json.sample .clasp.json
# .clasp.json の "YOUR_SCRIPT_ID" を実際のスクリプトIDに書き換える
# （スクリプトIDはGASエディタの「プロジェクトの設定 > ID」で確認できます）
```

コードをpushして、ライブラリとしてデプロイします:

```bash
npx clasp push
npx clasp deploy -d "初回デプロイ"
```

`clasp deploy` の出力に表示される**バージョン番号**（`@1` の `1`）と、このプロジェクトの**スクリプトID**を控えておいてください。次の手順で使います。

#### 3. テンプレートドキュメント（caller）の作成

1. 記事執筆の元となるGoogleドキュメント（テンプレート）を新規作成します。
2. そのドキュメントのメニュー「拡張機能 > Apps Script」を開きます。これでコンテナバインドのGASプロジェクトが作られます。
3. 開いたGASエディタの「プロジェクトの設定 > ID」からスクリプトIDをコピーします。
4. ローカルで `caller/.clasp.json` と `caller/src/appsscript.json` をサンプルから作成します:

```bash
cd caller
cp clasp.json.sample .clasp.json
# .clasp.json の "YOUR_SCRIPT_ID" を手順3でコピーしたスクリプトIDに書き換える

cp src/appsscript.json.sample src/appsscript.json
# src/appsscript.json の "YOUR_LIBRARY_ID_HERE" を手順2のライブラリのスクリプトIDに、
# "version" を手順2で控えたバージョン番号（例: "1"）に書き換える
```

5. コンテナバインドプロジェクトへpushします（自動生成された初期ファイルを上書きするため `--force` が必要です）:

```bash
npx clasp push --force
```

6. テンプレートドキュメントをブラウザで再読み込みすると、メニューに「サイト更新」が表示されます。

#### 4. 接続情報の設定

テンプレートドキュメントのメニュー「サイト更新 > 設定」から、GitHubのユーザー名・リポジトリ名・PAT（Personal Access Token）などを設定します。初回実行時はGoogleの承認画面が表示されるので許可してください。PATの発行方法は後述の「[セキュリティ](#セキュリティ)」の推奨事項を参照してください。

> 2回目以降のライブラリ更新は `./deploy_library.sh` で、push・デプロイ・callerのバージョン更新までまとめて実行できます（`jq` が必要です）。

### ライター向け：記事の公開フロー

1.  **記事の作成**: 開発者から共有されたテンプレートドキュメントをコピーして、新しい記事の執筆を開始します。
2.  **メタデータ入力**: メニューの「サイト更新 > フロントマターを挿入」を実行し、記事のタイトルや公開日などを入力します。
3.  **執筆と画像の挿入**: 本文を書き、必要な画像をドキュメントに貼り付けます。
4.  **プレビュー**: 「サイト更新 > Markdownプレビュー」で、実際の表示に近い形で内容を確認できます。
5.  **公開**: 執筆が完了したら、「サイト更新 > GitHubへPush」をクリック。これだけで公開作業は完了です！

## セキュリティ

### PAT（GitHubアクセストークン）の保存方式

PATは**ライブラリスクリプトのScriptProperties**に、ドキュメントIDをキー（`GITHUB_TOKEN_<ドキュメントID>`）として保存されます。リポジトリ名などトークン以外の設定は、各ドキュメントのドキュメントプロパティに保存されます。

この方式が成立する根拠は、Google Apps Scriptの仕様にあります。

- ライブラリのScriptPropertiesは呼び出し元スクリプトと**共有されません**（[公式ドキュメントの "not-shared resource"](https://developers.google.com/apps-script/guides/libraries)）。そのため、ドキュメントの編集権限を持つ人がバインドスクリプトを開いても、ライブラリ側に保存されたトークンを直接読み出すことはできません。
- トークンを扱うライブラリ内部の関数は、すべて**末尾アンダースコア命名**（例: `getSettingsInternal_`）にしています。GASの仕様で、末尾アンダースコアの関数はライブラリ利用者から見えず、呼び出すこともできません。**この命名規約を崩すとトークンが取り出せるようになるため、トークンを扱う関数を追加する際は必ず末尾アンダースコアを付けてください。**
- 公開API `getSettings()` はトークンを返しません。設定済みかどうかを示す `HAS_TOKEN` フラグのみ返します。

### なぜ暗号化ではなく「保存場所の分離」なのか（設計判断）

PATを暗号化して保存する案も検討しましたが、採用していません。GASでは暗号鍵を置ける場所もまたプロパティストアしかないため、暗号化しても「秘密を守る境界」はライブラリのプロパティから変わらず、第三者の暗号ライブラリへの依存と鍵管理の複雑さだけが増えるからです。トークンを最初からライブラリ側のプロパティに置けば、同じ境界をより単純な仕組みで守れます。

### 信頼モデル（誰が何をできるか）

| 立場                             | できること                                                                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| ライブラリの編集権限を持つ開発者 | トークンの閲覧・変更が可能（ScriptPropertiesを直接見られるため）。**ライブラリのデプロイ者を信頼することがこのツールの前提です。** |
| ドキュメントの編集者（ライター） | 保存済みトークンを使った「設定されたリポジトリへのPush」は実行可能（これは機能そのもの）。トークンの値は取得不可。                 |
| ドキュメントの閲覧者             | 何もできません。                                                                                                                   |

### 運用上の注意点

- **旧バージョンからの移行**: 旧バージョンはPATを各ドキュメントのドキュメントプロパティに平文で保存していました。ライブラリ更新後、各ドキュメントの「サイト更新 > 設定」からPATを設定し直してください。ドキュメントプロパティに残っていた旧トークンは、設定を保存し直したときに自動削除されます。なお、旧バージョンのトークンはドキュメントの編集権限があれば読める状態だったため、移行時は同じ値を使い回さず、**新しく発行したPATに差し替える**ことを推奨します。
- **ドキュメントをコピーした場合**: トークンはドキュメントIDに紐付くため、コピー先には引き継がれません（コピー先で再設定が必要）。ライターがテンプレートをコピーして使う運用では、コピーのたびに開発者がトークンを設定するか、ライターにトークン設定を依頼する必要がある点に注意してください。
- **ドキュメントを削除した場合**: 対応するトークンはライブラリのScriptPropertiesに残り続けます。不要になったトークンは、ライブラリプロジェクトの「プロジェクトの設定 > スクリプト プロパティ」から `GITHUB_TOKEN_<ドキュメントID>` を削除してください。
- **容量制限**: ScriptPropertiesの上限は合計500KB・1値あたり9KBです。トークンは1件あたり100バイト未満なので、通常の利用で問題になることはありません。

### 推奨事項

- **Fine-grained PAT**を使用し、対象を公開先リポジトリ1つに限定、権限は `Contents: Read and write` のみとする。classic PATの `repo` スコープは全リポジトリに書き込めるため使わないでください。
- PATには**有効期限**を設定し、定期的にローテーションする。漏えいを疑う場合は、GitHub側でトークンを失効させれば即座に無効化できます。
- ライブラリスクリプトのオーナー権限・編集権限を厳格に管理する（上記の信頼モデルのとおり、ここがこのツールの信頼の root です）。

## 開発

開発やデプロイを補助するスクリプトを用意しています。

- **ライブラリの更新とデプロイ**:
  ```bash
  ./deploy_library.sh
  ```
- **古いデプロイのクリーンアップ**:
  ```bash
  ./rm_old_deploy.sh
  ```
- **CI/CD**: GitHub Actionsによる自動デプロイも設定済みです (`.github/workflows/deploy.yaml`)。
